# Team Working Agreement
## Communication
**Project meeting:** Every Wednesday at 6 PM ET (3 PM PT)
Discuss tasks, questions, and concerns.
Zoom: Project meeting

**Standup meeting:** Every Thursday at 9 PM ET (6 PM PT)
Brief updates on each team member's current tasks.
Slack: #fall26-py-team2

Project meetings and task updates are important for maintaining a smooth workflow and completing the project on time.

- Team members should attend project meetings whenever possible.
- Issues and blockers should be reported to the team as soon as possible.
- Team members should provide timely updates on their tasks.
- Tasks that may block other team members should be prioritized and completed first.
- Team members should notify the team in advance if they expect to be absent for more than 5 days so that their tasks can be reassigned if needed.

## Git Workflow
- New work should be done on a feature branch, not directly on 'main'.
- All code and documentation changes should be submitted through a pull request.
- Team members should pull the latest changes from 'main' before starting new work when appropriate.
- Commit messages should clearly describe the changes. 
- Pull requests should have a clear title and a concise but comprehensive description. The title should start with the relevant ticket number, such as AIR-X or KAN-X

## Tasks
All the tasks are stored in Jira (https://practicumteam2.atlassian.net/jira/software/projects/KAN/list?jql=project%20%3D%20KAN%20ORDER%20BY%20cf%5B10019%5D%20ASC)
- Team members can assign tasks to themselves.
- MUST tasks have the highest priority and should be completed first.
- SHOULD tasks are completed when the team has enough time and resources.
- COULD tasks have the lowest priority and can be completed if time allows.

## Blockers
Blockers should be raised in the team chat **as soon as possible**.
When raising a blocker, briefly describe:
- what is blocking you
- what you have already tried
- what help you need

PR-specific blockers can also be discussed in the PR comments.

## Availability and Response Times
Teammates should respond to review requests within **24 hours** when possible. 
If they cannot review within that time, they should let the author know when they expect to be available.

## Pull Request
Before a pull request is merged:
- At least one teammate must review it.
- All requested changes and review comments must be addressed.
- All required automated checks must pass.
- The PR should be approved by the reviewer.
- The author should confirm that the changes are ready to merge.

## Roles and Opportunities
We will rotate responsibilities across the team when possible. PR reviews, documentation, Git tasks, and other learning opportunities should be shared so that each team member can gain experience with different parts of the workflow.
